# Card Forge 데이터베이스 구조 — Supabase

> 규칙 버전: `card-database-rules-v1`
> 상태: 구현 기준 확정 ·

## 1. 설계 방향

토스로 로그인한 사용자를 식별하고, 해당 사용자가 어떤 카드를 몇 강화 상태로 보유하고 있는지만 저장한다.

**Supabase 프로젝트의 PostgreSQL 데이터베이스에 3개의 테이블**을 구성한다. 모든 계정 및 보유 카드의 원본 데이터는 백엔드인 Supabase에 저장한다. 앱의 로컬 데이터는 화면 표시를 위한 임시 캐시로만 사용한다. 계정용·카드용·보유 카드용 데이터베이스를 각각 따로 만들 필요는 없다.

| 테이블 | 역할 | 저장 단위 |
| --- | --- | --- |
| `users` | 토스 로그인 계정 식별 | 사용자 1명당 1행 |
| `cards` | 총 36종의 카드 기본 정보 | 카드 종류당 1행, 총 36행 |
| `user_cards` | 사용자가 보유한 카드와 강화 수치 | 실제 보유 카드 1장당 1행 |

36장은 카드의 **종류 수**이며, 사용자별 보유 한도와는 별개다. 사용자별 보유 한도는 기존 정책인 **최대 5장**을 적용한다.

## 2. 계정 테이블 — `users`

토스 로그인으로 확인한 사용자 식별값과 서비스 내부 사용자 ID를 연결한다.

| 컬럼 | 타입 | 조건 | 설명 |
| --- | --- | --- | --- |
| `id` | `bigint` | 기본키, 자동 생성 | 서비스 내부 사용자 ID |
| `toss_user_id` | `text` | 필수, 중복 불가 | 서버에서 토스 로그인 검증 후 확인한 사용자 식별값 |

- 최초 로그인: 계정이 없으면 생성한다.
- 재로그인: 동일한 `toss_user_id`에 연결된 기존 계정을 사용한다.
- 비밀번호, 전화번호, 실명은 이 구조에 저장하지 않는다.
- `toss_user_id`는 문서에서 정한 DB 컬럼명이다. 실제 토스 응답 필드와의 연결은 로그인 구현 시 확정한다. 로그인 토큰을 계정 ID 대신 사용하지 않는다.

## 3. 카드 기본 정보 테이블 — `cards`

모든 사용자가 공통으로 참조하는 36종의 카드 정보를 저장한다.

| 컬럼 | 타입 | 조건 | 설명 |
| --- | --- | --- | --- |
| `id` | `bigint` | 기본키 | 카드 종류 ID |
| `name` | `text` | 필수 | 카드 이름 |
| `image_path` | `text` | 선택 | 카드 이미지 경로 또는 URL |

- 초기 데이터로 36종을 등록하고, 사용자가 카드를 뽑을 때는 이 테이블을 추가하거나 수정하지 않는다.
- 강화 수치는 카드 종류의 공통 속성이 아니므로 여기에 저장하지 않는다.
- 등급, 속성, 기본 능력치는 게임에서 실제로 필요해질 때 추가한다.

## 4. 보유 카드 테이블 — `user_cards`

누가 어떤 카드를 보유하고 있으며, 그 카드가 몇 강화인지 저장한다.

| 컬럼 | 타입 | 조건 | 설명 |
| --- | --- | --- | --- |
| `id` | `bigint` | 기본키, 자동 생성 | 보유 카드 한 장의 고유 ID |
| `user_id` | `bigint` | 필수, 외래키 → `users.id` | 카드 소유자 |
| `card_id` | `bigint` | 필수, 외래키 → `cards.id` | 카드 종류 |
| `enhancement_level` | `integer` | 필수, 기본값 0, 0 이상 | 현재 강화 수치 |

**보유한 카드만 행으로 저장한다.** 사용자마다 36종 전체에 대해 빈 보유 데이터를 만들지 않는다.

동일한 종류를 여러 장 보유할 수 있는 구조를 기본안으로 한다. 중복 카드를 금지하는 게임 규칙은 아직 확정하지 않았으므로 `(user_id, card_id)`에 중복 금지 조건을 걸지 않는다. 같은 종류라도 각 카드의 `id`가 달라 강화 수치를 따로 관리할 수 있다.

## 5. 테이블 연결

- `users` 1명에 `user_cards` 여러 장이 연결된다.
- `cards` 1종은 여러 사용자의 `user_cards`에서 참조할 수 있다.
- 보관함은 `user_cards`를 기준으로 `cards`를 연결해 카드 이름·이미지·강화 수치를 함께 조회한다.

카드 이름과 이미지를 보유 카드마다 복사하지 않고, `card_id`로 공통 정보를 참조한다.

## 6. 기본 동작 규칙

### 로그인

1. 서버에서 토스 로그인을 검증하고 사용자 식별값을 확인한다.
2. `users.toss_user_id`로 기존 사용자를 찾는다.
3. 없으면 생성하고, 해당 내부 사용자 ID로 보유 카드를 조회한다.

사용자 식별은 검증된 로그인 정보를 기준으로 한다. 클라이언트가 보낸 `user_id`만 믿고 다른 계정의 카드에 접근하게 해서는 안 된다.

### 카드 뽑기

1. 해당 사용자의 실제 보유 카드 수를 확인한다.
2. **5장 이상이면 뽑기를 거절한다.**
3. 5장 미만이면 서버에서 카드 종류를 결정한다.
4. `user_cards`에 강화 수치 0으로 새 카드를 저장한다.

보유 수 확인과 카드 추가는 하나의 트랜잭션으로 처리하고, 같은 계정의 뽑기 요청은 직렬화한다. Supabase의 PostgreSQL 함수 내부에서 사용자 행을 잠그고 보유 수 확인과 추가를 함께 수행하는 방식으로 구현한다. 별도의 API 요청으로 COUNT와 INSERT를 나누지 않는다. 단순히 확인 후 추가하는 것만으로는 동시 뽑기에서 5장을 초과할 수 있다.

### 카드 강화

1. 보유 카드의 `id`로 대상을 찾는다.
2. 로그인한 사용자의 카드인지 확인한다.
3. 서버에서 강화 결과를 결정하고 해당 행의 `enhancement_level`을 변경한다.

클라이언트가 지정한 강화 수치를 그대로 저장하지 않는다. 최대 강화 수치는 게임 규칙 확정 후 검증 조건에 반영한다.

### 보관함 조회

- `user_id`로 조회하고 `user_cards.id` 오름차순으로 정렬한다.
- 화면에는 앞의 5장만 표시한다.
- 오류로 5장을 초과해 저장되어 있어도 조회 과정에서 초과 카드를 삭제하지 않는다.
- 뽑기 가능 여부는 화면에 표시한 수가 아닌 **DB의 실제 보유 수**로 판단한다.
- 3장·4장·5장에 따른 화면 배치는 UI에서 처리하며, 별도 DB 컬럼은 필요하지 않다.

## 7. 최소 제약조건과 인덱스

| 대상 | 설정 | 목적 |
| --- | --- | --- |
| `users.toss_user_id` | UNIQUE, NOT NULL | 같은 토스 계정의 중복 등록 방지 |
| `user_cards.user_id` | 외래키, NOT NULL | 존재하는 사용자에게만 연결 |
| `user_cards.card_id` | 외래키, NOT NULL | 등록된 카드 종류만 보유 가능 |
| `user_cards.enhancement_level` | NOT NULL, DEFAULT 0, CHECK ≥ 0 | 음수 강화 수치 방지 |
| `user_cards(user_id, id)` | 복합 인덱스 | 사용자별 보관함 조회와 정렬 지원 |

카드 종류는 참조 중인 보유 카드가 있으면 삭제를 제한한다. 사용자 삭제 시 연결된 보유 카드는 함께 삭제하는 정책을 기본안으로 한다.

## 8. 현재 범위에서 제외하는 항목

별도의 강화 이력, 뽑기 이력, 거래 이력, 재화, 인벤토리 요약 테이블은 만들지 않는다. 보유 카드 수는 `user_cards`에서 계산하므로 `users`에 중복 저장하지 않는다.

현재 요구사항은 **계정 식별 + 카드 36종 + 실제 보유 카드와 강화 수치**를 저장하는 3개 테이블로 구성한다. 이 문서는 설계안이며 실제 DB 생성이나 앱 코드 변경은 포함하지 않는다.

| 인증 및 게임 처리 API | 토스 로그인 검증, 세션 확인, 소유자 확인, 뽑기·강화 규칙 실행 |
| Supabase PostgreSQL | `users`, `cards`, `user_cards` 저장 및 트랜잭션 처리 |

Supabase는 PostgreSQL 데이터베이스를 제공한다. 위의 3개 테이블은 모두 이 DB에 생성한다. [Supabase 공식 소개](https://supabase.com/)

### 토스 로그인과 계정 연결

이 설계의 `users`는 게임용 계정 테이블이며 Supabase Auth의 `auth.users`와는 별개다. 토스 로그인 결과가 자동으로 Supabase Auth 세션이 된다고 가정하지 않는다.

기본안은 **앱이 인증 및 게임 처리 API를 호출하고, API가 Supabase에 접근하는 방식**이다. API가 검증한 토스 사용자 식별값을 `users.toss_user_id`에 연결한다. API의 실행 환경과 토스 인증 연동 세부 구현은 별도로 확정한다.

### DB 접근 권한

- 앱에서 계정·보유 카드 테이블을 직접 읽거나 수정하지 않도록 구성한다.
- 외부에 노출되는 스키마의 테이블에는 RLS를 활성화하고, `anon`·`authenticated` 역할의 불필요한 접근 권한을 제거한다. [Supabase RLS 문서](https://supabase.com/docs/guides/database/postgres/row-level-security)
- 서버 전용 비밀 키는 API 실행 환경에만 저장한다. RLS를 우회하는 서버 권한으로 접근할 경우 API가 세션과 카드 소유자를 직접 검증해야 한다. [Supabase 역할 문서](https://supabase.com/docs/guides/database/postgres/roles)
- 카드 뽑기 및 강화용 DB 함수도 일반 앱 사용자가 직접 실행할 수 없도록 호출 권한을 제한한다.

Supabase를 사용해도 테이블 수는 늘리지 않는다. 현재 범위에서는 기존 3개 테이블과 이를 처리하는 API·DB 함수로 구성한다.
