# Card Forge 데이터베이스 구조 — Supabase

> 규칙 버전: `card-database-rules-v2`
> 상태: 구현 기준 확정

## 1. 설계 방향

토스의 `getUserKeyForGame()` 식별값을 서버에서 HMAC-SHA256으로 해시한 뒤 사용자 식별값으로 사용한다. 원문 식별값은 DB에 저장하지 않고 `users.hash_id`에 64자리 해시값만 저장한다.

Supabase PostgreSQL에는 기본적으로 3개의 테이블을 사용한다.

| 테이블 | 역할 | 저장 단위 |
| --- | --- | --- |
| `users` | 사용자 식별, 닉네임, 대표 캐릭터 카드, 결정 수 관리 | 사용자 1명당 1행 |
| `cards` | 총 36종의 카드 기본 정보 | 카드 종류당 1행 |
| `user_cards` | 사용자가 실제 보유한 카드와 강화 수치 | 보유 카드 1장당 1행 |

사용자별 보유 한도는 최대 5장이다.

## 2. 계정 테이블 — `users`

| 컬럼 | 타입 | 조건 | 설명 |
| --- | --- | --- | --- |
| `id` | `bigint` | 기본키, 자동 생성 | 서비스 내부 사용자 ID |
| `hash_id` | `text` | 필수, `UNIQUE` | `getUserKeyForGame()` 식별값을 서버에서 HMAC-SHA256 처리한 사용자 고유 해시 |
| `nickname` | `text` | 필수, 기본값 `모험가` | 게임에서 표시할 사용자 닉네임 |
| `characters_card_id` | `bigint` | 선택, 외래키 → `cards.id`, 삭제 시 `NULL` | 사용자가 대표 캐릭터로 선택한 카드 종류 ID |
| `crystal_balance` | `bigint` | 필수, 기본값 0, 0 이상 | 현재 보유 결정 수 |
| `total_crystals_earned` | `bigint` | 필수, 기본값 0, 0 이상 | 가입 이후 누적 획득 결정 수 |
| `pack_opened_on` | `date` | 선택 | 카드팩 일일 제한 기준 날짜 |
| `pack_open_count` | `integer` | 필수, 기본값 0 | 해당 날짜의 카드팩 오픈 횟수 |
| `pack_request_receipts` | `jsonb` | 필수, 기본값 `{}` | 카드팩 요청 중복 처리 방지용 영수증 |
| `card_sale_request_receipts` | `jsonb` | 필수, 기본값 `{}` | 카드 판매 요청 중복 처리 방지용 영수증 |

### 사용자 식별 규칙

- 최초 접속 시 `hash_id`가 없으면 새 사용자 행을 만든다.
- 재접속 시 동일한 `hash_id`의 기존 사용자 행을 사용한다.
- `hash_id`에는 `UNIQUE` 제약을 둬 동일 사용자가 중복 생성되지 않도록 한다.
- 토스 원본 사용자 식별값, 비밀번호, 전화번호, 실명은 저장하지 않는다.
- 현재 구현은 `SESSION_PEPPER`를 이용한 HMAC-SHA256 결과를 `hash_id`로 저장한다.
- 로그인 토큰 자체를 사용자 ID로 저장하지 않는다.

## 3. 카드 기본 정보 테이블 — `cards`

모든 사용자가 공통으로 참조하는 36종의 카드 정보를 저장한다.

| 컬럼 | 타입 | 조건 | 설명 |
| --- | --- | --- | --- |
| `id` | `bigint` | 기본키 | 카드 종류 ID |
| `name` | `text` | 필수 | 카드 이름 |
| `element` | `text` | 필수 | 땅, 물, 바람, 불, 빛, 어둠 |
| `rarity` | `text` | 필수 | 노말, 매직, 레어, 슈퍼레어, 유니크, 레전더리 |
| `image_path` | `text` | 선택 | Supabase Storage 카드 이미지 객체 키 |

초기 데이터로 36종을 등록하고, 사용자가 카드를 뽑을 때 이 테이블 자체를 추가하거나 수정하지 않는다. 강화 수치는 카드 종류의 공통 속성이 아니므로 `user_cards`에 저장한다.

## 4. 보유 카드 테이블 — `user_cards`

| 컬럼 | 타입 | 조건 | 설명 |
| --- | --- | --- | --- |
| `id` | `bigint` | 기본키, 자동 생성 | 보유 카드 한 장의 고유 ID |
| `user_id` | `bigint` | 필수, 외래키 → `users.id` | 카드 소유자 |
| `card_id` | `bigint` | 필수, 외래키 → `cards.id` | 카드 종류 |
| `enhancement_level` | `integer` | 필수, 기본값 0, 0 이상 | 현재 강화 수치 |

보유한 카드만 행으로 저장한다. 동일한 종류의 카드를 여러 장 보유할 수 있으므로 `(user_id, card_id)`에는 `UNIQUE` 제약을 두지 않는다.

## 5. 테이블 연결

- `users.id` 1개에 여러 `user_cards.user_id`가 연결된다.
- `cards.id` 1개는 여러 사용자의 `user_cards.card_id`에서 참조할 수 있다.
- `users.characters_card_id`는 대표 캐릭터 카드 한 종류를 `cards.id`로 참조한다.
- 대표 캐릭터 카드가 삭제될 경우 `characters_card_id`는 `NULL`로 변경한다.
- 사용자 삭제 시 연결된 `user_cards`는 함께 삭제하는 정책을 사용한다.

## 6. 기본 동작 규칙

### 로그인 / 사용자 초기화

1. 앱에서 토스 `getUserKeyForGame()` 식별값을 서버로 전달한다.
2. 서버에서 필요한 검증을 수행한다.
3. 서버가 `SESSION_PEPPER`로 HMAC-SHA256 해시를 생성한다.
4. 생성된 64자리 값을 `users.hash_id`에서 조회한다.
5. 없으면 새 사용자 행을 생성한다.
6. 새 사용자라면 `nickname = '모험가'`, `characters_card_id = NULL` 상태로 시작한다.

클라이언트가 보낸 내부 `user_id`만 믿고 다른 계정의 데이터에 접근하게 해서는 안 된다.

### 닉네임

- 기본값은 `모험가`다.
- 이후 닉네임 변경 API를 추가할 경우 서버에서 길이와 허용 문자를 검증한 뒤 변경한다.
- 현재 DB에는 컬럼만 준비되어 있으며 프로필 PATCH API 구현은 별도 작업이다.

### 대표 캐릭터 카드

- `characters_card_id`는 `cards.id`를 참조한다.
- 선택하지 않은 상태는 `NULL`이다.
- 대표 캐릭터는 카드 종류를 가리키며, 특정 사용자가 실제로 소유한 `user_cards.id`를 가리키는 값은 아니다.
- 실제 보유 카드만 대표 캐릭터로 선택하도록 제한하려면 API에서 소유 여부를 추가 검증한다.

### 결정 획득 및 사용

- 결정 획득 시 `crystal_balance`와 `total_crystals_earned`를 한 트랜잭션에서 함께 증가시킨다.
- 결정 사용 시 `crystal_balance`만 감소시키고 `total_crystals_earned`는 유지한다.
- 잔액 검증과 차감은 원자적으로 처리해 동시 요청에서도 음수가 되지 않도록 한다.

### 카드 뽑기

1. 해당 사용자의 실제 보유 카드 수를 확인한다.
2. 5장 이상이면 뽑기를 거절한다.
3. 5장 미만이면 서버에서 카드 종류를 결정한다.
4. `user_cards`에 강화 수치 0으로 새 카드를 저장한다.

보유 수 확인과 INSERT는 하나의 DB 트랜잭션/함수 안에서 처리한다.

### 카드 강화

1. `user_cards.id`로 강화 대상을 찾는다.
2. 로그인한 사용자의 카드인지 확인한다.
3. 서버에서 강화 성공 여부를 결정한다.
4. 성공한 경우 서버가 `enhancement_level`을 변경한다.

### 보관함 조회

- `user_id` 기준으로 조회한다.
- 최대 5장까지만 UI에 표시한다.
- DB 오류로 5장을 초과한 경우에도 조회 과정에서 임의 삭제하지 않는다.
- 뽑기 가능 여부는 UI 표시 수가 아니라 DB의 실제 보유 수로 판단한다.

## 7. 최소 제약조건과 인덱스

| 대상 | 설정 | 목적 |
| --- | --- | --- |
| `users.hash_id` | `UNIQUE`, `NOT NULL` | 같은 사용자 해시의 중복 등록 방지 |
| `users.nickname` | `NOT NULL`, `DEFAULT '모험가'` | 사용자 닉네임 기본값 유지 |
| `users.characters_card_id` | FK → `cards.id`, nullable, `ON DELETE SET NULL` | 대표 캐릭터 카드 참조 |
| `users.crystal_balance` | `NOT NULL`, `DEFAULT 0`, `CHECK >= 0` | 현재 보유 결정 음수 방지 |
| `users.total_crystals_earned` | `NOT NULL`, `DEFAULT 0`, `CHECK >= 0` | 누적 획득 결정 음수 방지 |
| `user_cards.user_id` | FK, `NOT NULL` | 존재하는 사용자에게만 연결 |
| `user_cards.card_id` | FK, `NOT NULL` | 등록된 카드 종류만 보유 가능 |
| `user_cards.enhancement_level` | `NOT NULL`, `DEFAULT 0`, `CHECK >= 0` | 음수 강화 수치 방지 |
| `user_cards(user_id, id)` | 복합 인덱스 | 사용자별 보관함 조회 및 정렬 지원 |

## 8. 현재 DB 변경 이력

2026-09-12 변경:

- `users.toss_user_id` → `users.hash_id`로 컬럼명 변경
- 기존 값은 그대로 유지
- 기존 `UNIQUE` 제약도 `hash_id`에 유지
- `users.nickname text NOT NULL DEFAULT '모험가'` 추가
- `users.characters_card_id bigint NULL` 추가
- `users.characters_card_id → cards.id` 외래키 추가
- 기존 회원 초기화 함수는 `users.hash_id`를 기준으로 조회/생성하도록 변경

과거에 이미 적용된 migration 파일은 이력 보존을 위해 수정하지 않고, 새로운 migration에서 현재 구조로 변경한다.

## 9. Supabase 적용 방식

`users`, `cards`, `user_cards`는 앱이 직접 쓰지 않고 Supabase Edge Function과 서버 전용 DB 함수에서 처리한다.

- 공개 클라이언트에 `service_role`/secret key를 노출하지 않는다.
- 외부 노출 스키마의 테이블에는 RLS를 유지한다.
- `anon`/`authenticated`가 서버 전용 RPC를 직접 호출하지 못하도록 권한을 회수한다.
- 서버 API는 세션과 사용자 소유권을 검증한 뒤 DB 함수를 호출한다.
- `hash_id`는 토스 식별값 원문이 아니라 서버에서 생성한 해시값이다.
