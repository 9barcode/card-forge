# Card Forge 서버 구성 추천

## 목적

Apps in Toss 기반 `card-forge`에서 사용자 정보, 카드 보유 정보, 재화, 카드팩, 강화, 교환, 거래 기록 등의 데이터를 안전하게 저장하고 처리하기 위한 서버 구성을 정리한다.

현재 프로젝트는 이미 `apps/server`에 Node.js/NestJS 기반 백엔드가 존재하고, PostgreSQL 저장소 계층과 Toss mTLS 클라이언트도 구현되어 있다.

따라서 단순히 가장 싼 서비스만 고르는 것보다 아래 두 기준으로 나누는 것이 적절하다.

- **실전 운영 1순위:** Railway + PostgreSQL
- **최저 비용 1순위:** Cloudflare Workers + D1

---

## 결론부터

현재 `card-forge`에는 다음 구성을 가장 추천한다.

> **Railway + PostgreSQL**

이유는 현재 서버 코드 구조를 거의 그대로 배포할 수 있고, Toss mTLS 연동이나 일반 Node.js 서버 기능을 사용하는 데 제약이 적기 때문이다.

비용을 극단적으로 줄여야 하고 서버 구조 변경도 감수할 수 있다면 Cloudflare Workers + D1을 대안으로 사용할 수 있다.

# 1순위: Railway + PostgreSQL

## 추천 구조

```text
Apps in Toss
     │
     │ HTTPS
     ▼
Railway
NestJS / Node.js API
     │
     ├── 사용자 인증
     ├── Toss mTLS 통신
     ├── 카드 조회
     ├── 카드팩 개봉
     ├── 강화
     ├── 교환
     ├── 재화 처리
     ├── 광고 보상 검증
     └── 부정행위 방지
     │
     ▼
PostgreSQL
```

현재 프로젝트의 `apps/server`가 이미 이 구조에 매우 가깝다.

```text
apps/server/
├── src/
│   ├── cards/
│   ├── packs/
│   ├── enhancement/
│   ├── exchange/
│   ├── membership/
│   ├── fraud-detection/
│   ├── database/
│   └── toss/
├── migrations/
└── package.json
```

즉 Railway를 사용할 경우 서버를 Cloudflare Worker 방식으로 다시 작성하지 않고 기존 NestJS 서버를 그대로 활용할 수 있다는 점이 가장 크다.

---

## Railway를 추천하는 이유

### 1. 기존 서버 구조를 그대로 사용할 수 있음

Railway는 일반적인 Node.js 서버를 실행할 수 있으므로 다음과 같은 서버 코드를 그대로 배포할 수 있다.

```ts
await app.listen(process.env.PORT || 3000);
```

NestJS, Express, Fastify 등 일반적인 Node 서버 구조를 거의 그대로 사용할 수 있다.

### 2. PostgreSQL을 바로 연결 가능

현재 `card-forge` 서버는 PostgreSQL 기반 Repository와 migration 구조를 이미 사용하고 있기 때문에 Railway PostgreSQL과 궁합이 좋다.

```text
NestJS API
    │
    ▼
PostgreSQL
 ├── users
 ├── cards
 ├── user_cards
 ├── transactions
 ├── packs
 └── game state
```

Cloudflare D1로 옮기면 SQL 및 DB 접근 계층을 일부 수정해야 하지만 Railway PostgreSQL에서는 수정 범위가 훨씬 작다.

### 3. Toss mTLS 서버 통신에 유리

Apps in Toss의 서버 API 중 일부는 파트너 서버와 Toss 서버 간 mTLS 인증이 필요하다.

현재 프로젝트에도 Toss mTLS 클라이언트 코드가 존재하므로, 일반 Node.js 런타임에서 인증서와 HTTPS Agent 등을 자유롭게 제어할 수 있는 Railway가 유리하다.

```text
Apps in Toss Client
       │
       ▼
Railway Backend
       │
       │ mTLS
       ▼
Apps in Toss Server API
```

### 4. GitHub 배포가 쉬움

GitHub 저장소를 Railway에 연결하면 일반적으로 다음 흐름으로 운영할 수 있다.

```text
git push
   ↓
Railway 자동 빌드
   ↓
NestJS 서버 재배포
   ↓
PostgreSQL 연결
```

초기 개인 프로젝트에서 별도의 CI/CD 서버를 직접 운영할 필요가 없다.

### 5. 서버 관리가 거의 필요 없음

VPS를 직접 운영하면 다음 작업이 필요하다.

```text
Ubuntu 업데이트
Node 설치
PM2/systemd 설정
Nginx
HTTPS 인증서
방화벽
PostgreSQL 설치/백업
로그 관리
```

Railway를 사용하면 이런 관리 부담을 상당 부분 줄일 수 있다.

---

## Railway 비용 관점

Railway는 완전 무료 영구 서버라기보다 **소규모 사용량 기반의 저비용 관리형 서버**로 보는 것이 맞다.

개발/테스트 단계에서는 무료 또는 매우 적은 비용으로 시작할 수 있지만, 실제 서비스를 안정적으로 계속 운영한다면 대략 월 **$5 이상**을 기본 예산으로 생각하는 편이 안전하다.

실제 요금은 CPU, RAM, 네트워크, DB 사용량에 따라 달라질 수 있다.

또한 Usage Limit 또는 Hard Limit 같은 비용 제한 기능을 설정해 예상보다 트래픽이 커졌을 때 과금이 급격히 증가하는 것을 방지하는 것이 좋다.

> Railway 가격과 무료 크레딧 정책은 변경될 수 있으므로 출시 직전에 공식 Pricing 문서를 다시 확인한다.

# 2순위: Cloudflare Workers + D1

비용만 보면 Cloudflare Workers + D1이 가장 강력하다.

```text
Apps in Toss
     │
     ▼
Cloudflare Workers
     │
     ├── REST API
     ├── 게임 로직
     └── 인증
     │
     ▼
Cloudflare D1
```

## 장점

- 초기 비용을 거의 0원으로 시작 가능
- 서버가 놀고 있어도 VPS처럼 고정 서버비가 발생하지 않음
- 글로벌 Edge 네트워크 사용 가능
- 서버 관리가 필요 없음
- TypeScript 사용 가능

## 단점

현재 `card-forge`에는 이미 일반 Node/NestJS 서버가 있기 때문에 Worker로 이동하려면 일부 구조를 변경해야 한다.

특히 다음 부분을 다시 확인해야 한다.

- Node.js API 호환성
- PostgreSQL → D1 이전
- DB Repository 수정
- migration SQL 수정
- mTLS 인증서 처리
- 장시간 실행되는 작업
- 특정 Node 모듈 호환성

따라서 **신규 프로젝트라면 좋은 선택이지만 현재 프로젝트에서는 Railway보다 마이그레이션 비용이 높다.**

---

## Cloudflare 무료 운영 예시

예를 들어 사용자 1,000명이 하루 평균 API를 30번 호출하면:

```text
1,000명 × 30회
= 30,000 API 요청 / day
```

초기 규모에서는 무료 구간 안에서 운영될 가능성이 높다.

하지만 D1은 PostgreSQL이 아니라 SQLite 계열이므로 현재 서버 DB 구조를 그대로 사용할 수 있다고 가정하면 안 된다.

# 3순위: Supabase

Supabase는 PostgreSQL을 편하게 사용하고 싶은 경우 좋은 대안이다.

```text
Railway / Backend
       │
       ▼
Supabase PostgreSQL
```

또는 서버 로직이 단순하다면:

```text
Apps in Toss
     │
     ▼
Supabase
 ├── PostgreSQL
 ├── Auth
 ├── Storage
 └── Edge Functions
```

## 장점

- PostgreSQL
- 관리 UI 제공
- REST API 자동 생성
- 인증 기능
- Storage
- 무료 플랜 존재

## 단점

현재 프로젝트에서는 이미 NestJS 서버가 있기 때문에 Supabase의 Auth/API 기능을 모두 사용할 필요가 없다.

따라서 사용할 경우 **DB만 Supabase PostgreSQL로 사용하고 API 서버는 Railway에 두는 조합**도 가능하다.

```text
Apps in Toss
     │
     ▼
Railway NestJS
     │
     ▼
Supabase PostgreSQL
```

다만 서버와 DB를 같은 Railway 프로젝트에 두면 구성과 비용 관리가 더 단순할 수 있다.

---

# Firebase는 왜 우선순위가 낮은가

Firebase는 모바일 앱에서 사용하기 편하지만 현재 `card-forge` 데이터는 관계형 구조가 강하다.

예를 들면:

```text
User
 ├── Currency
 ├── Inventory
 │    └── Card
 ├── Pack History
 ├── Enhancement History
 └── Exchange History
```

이런 데이터는 PostgreSQL 같은 관계형 DB가 관리하기 편하다.

현재 서버 코드 역시 PostgreSQL 기반이므로 Firebase로 변경할 이유가 크지 않다.

---

# VPS / EC2는 언제 고려할까

사용자가 크게 늘거나 서버 운영을 직접 제어해야 할 필요가 생기면 VPS 또는 AWS/GCP 등의 VM을 고려할 수 있다.

```text
Apps in Toss
     │
     ▼
Nginx
     │
     ▼
NestJS
     │
     ▼
PostgreSQL
```

장점은 자유도가 높다는 것이지만 초기 프로젝트에서는 다음 관리 비용이 발생한다.

- OS 업데이트
- 보안 패치
- SSL
- Nginx
- 프로세스 관리
- DB 백업
- 로그
- 장애 대응

따라서 초기에는 Railway 같은 PaaS가 더 효율적이다.

# 추천 운영 단계

## 1단계 - 개발

```text
Local NestJS
     │
     ▼
Local PostgreSQL
```

서버/DB 로직 개발과 테스트를 진행한다.

## 2단계 - 외부 테스트

```text
Railway NestJS
     │
     ▼
Railway PostgreSQL
```

Apps in Toss 클라이언트와 실제 HTTPS API 통신을 확인한다.

## 3단계 - Toss 연동

```text
Apps in Toss
     │
     ▼
Railway
     │
     │ mTLS
     ▼
Toss Server API
```

인증서와 Toss 서버 API 연동을 검증한다.

## 4단계 - 출시

Railway에서 다음 항목을 설정한다.

- Production 환경변수
- PostgreSQL 백업 정책
- 로그 확인
- Health Check
- 비용 Usage Limit
- Custom Domain
- HTTPS
- Toss mTLS 인증서 Secret 관리

# 최종 추천

현재 프로젝트 상태에서는 **Railway + PostgreSQL을 기본 서버 구성으로 채택**하는 것을 추천한다.

가장 큰 이유는 이미 `card-forge` 서버가 Node/NestJS + PostgreSQL + Toss mTLS 형태로 구현되고 있기 때문이다.

따라서 Cloudflare의 무료 구간을 얻기 위해 서버 구조와 DB 계층을 다시 변경하는 것보다, Railway에 기존 서버를 그대로 배포하는 것이 개발 시간과 유지보수 비용까지 포함하면 더 저렴할 가능성이 높다.

```text
현재 추천

Apps in Toss
      ↓
Railway NestJS
      ↓
Railway PostgreSQL
```

향후 사용자가 크게 증가해 Railway 비용이 높아지는 시점에 Cloudflare, Supabase, 자체 VPS, AWS/GCP 등의 이전을 다시 검토한다.
